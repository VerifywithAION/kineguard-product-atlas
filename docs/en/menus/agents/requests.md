## 1. Purpose

Presents proposed actions before evaluation and handoff.

## 2. How the user operates it

1. Open Requests and distinguish fixture/demo from a runtime-submitted request.
2. Read intent, agent, target object, request data, budget and evidence context.
3. Run explicitly labeled simulations only; do not assume a request can sign.
4. Match the exact request with Decisions and then History.

## 3. Underlying mechanism

This route belongs to the Agents family and must be interpreted with identity, policy, exact request and evidence provenance.

## 4. Evidence and limitations

Requesting does not imply approval, forwarding or transfer execution.

A visible public screen does not equal human runtime acceptance or universal funds protection.
